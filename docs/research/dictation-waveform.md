# Dictation waveform

## Source facts

- OBS places its input meter before the volume fader and after source filters. The tap point determines which gain or processing the reading reflects. [OBS Audio Mixer Technical Details](https://obsproject.com/kb/audio-mixer-technical-details)
- The RTP client-to-mixer audio-level spec computes RMS over the samples encoded in each packet. JUCE's `BallisticsFilter` offers an RMS mode with attack and release controls that smooth the level over time. Web Audio exposes time-domain samples separately from its `AnalyserNode` smoothing, which blends FFT magnitudes across analysis blocks. [RFC 6464 §3](https://www.rfc-editor.org/rfc/rfc6464.html#section-3) · [JUCE BallisticsFilter](https://docs.juce.com/master/classjuce_1_1dsp_1_1BallisticsFilter.html) · [W3C Web Audio §1.8.6](https://www.w3.org/TR/webaudio/#fft-windowing-and-smoothing-over-time)
- With normalized full-scale sample amplitude `1.0`, `20 × log10(RMS)` gives sample-referenced dBFS RMS. A full-scale sine reads about −3.01 dBFS on that scale and 0 dBFS under the AES17 sine reference. [SMPTE ST 2095-1 §4](https://pub.smpte.org/pub/st2095-1/st2095-1-2023.pdf)
- Handy subtracts the mean from each 512-sample window at 16 kHz, applies a Hann window and FFT, and maps 16 frequency bands through display gain and a curve. The capture sink sends samples to the visualizer before VAD separately determines which audio frames to emit. [Window and bands](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/audio_toolkit/audio/sink.rs#L97-L125) · [Hann window](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/audio_toolkit/audio/visualizer.rs#L34-L42) · [Spectrum and display mapping](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/audio_toolkit/audio/visualizer.rs#L95-L143) · [Visualizer and VAD routing](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/audio_toolkit/audio/sink.rs#L181-L201)
- OpenWhispr computes time-domain RMS from byte samples for its live recording waveform and from float samples in its analyser helper. Its transcription microphone constraints set browser `autoGainControl` to `false` following a report of Windows microphone volume dropping during transcription. [Live waveform](https://github.com/OpenWhispr/openwhispr/blob/6d4a7d3679903df5a95fbb961d0dbfb87a2caf38/src/helpers/audioManager.js#L2156-L2183) · [Float RMS](https://github.com/OpenWhispr/openwhispr/blob/6d4a7d3679903df5a95fbb961d0dbfb87a2caf38/src/utils/audioLevel.ts#L1-L16) · [Microphone constraints](https://github.com/OpenWhispr/openwhispr/blob/6d4a7d3679903df5a95fbb961d0dbfb87a2caf38/src/helpers/microphoneSelection.js#L6-L15) · [Issue #476](https://github.com/OpenWhispr/openwhispr/issues/476)

## Device handling and model input

- **Handy** uses the system default or a selected capture device. It can average the input channels or use one selected channel, with an average as the fallback when the selected channel is unavailable. The recorder supplies 16 kHz mono. Optional voice activity detection filters which frames reach the recording. The FFT's mean removal and display gain are confined to the meter. [Device and channel handling](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/managers/audio.rs#L397-L448) · [Capture sink](https://github.com/cjpais/Handy/blob/e95d488805ed95268f5f0e7482b806c4d9851d51/src-tauri/src/audio_toolkit/audio/sink.rs#L173-L203)
- **OpenWhispr** resolves the system default, a built-in mic, or a specific mic from Chromium's device list. Its desktop transcription constraints turn off browser automatic gain, echo cancellation, and noise suppression. Its local batch PCM path uses a 16 kHz Web Audio context and produces mono PCM16, with the original WebM path available when the PCM copy is incomplete. [Microphone selection and constraints](https://github.com/OpenWhispr/openwhispr/blob/6d4a7d3679903df5a95fbb961d0dbfb87a2caf38/src/helpers/microphoneSelection.js#L7-L114) · [PCM capture and fallback](https://github.com/OpenWhispr/openwhispr/blob/6d4a7d3679903df5a95fbb961d0dbfb87a2caf38/src/helpers/pcmTap.js#L3-L88)
- **SmallTalkAI** resolves the preferred device or the system default, decodes supported PCM formats into floats, averages channels, resamples to 16 kHz, and applies the configured microphone gain before producing PCM16 for transcription. Mean removal affects only the visualization. The replay reproduced the display issue, and the model transcribed the quiet, biased fixture correctly with the existing input processing. [Device and capture path](../../src/capture/audio.rs#L288) · [Frame assembly and gain](../../src/capture/audio.rs#L135)

## Recommendation for SmallTalkAI

In one SmallTalkAI measurement, frame RMS p10/p90 was −19.2/−18.3 dBFS before mean subtraction and −60.1/−28.1 dBFS after subtracting each 20 ms frame’s mean. The wider spread shows how a steady offset can hide changes in signal level.

Measure after mono downmix and resampling and before optional app gain and PCM conversion. For the waveform, subtract each contiguous 320-sample frame’s mean before computing RMS. At 16 kHz this yields one level every 20 ms, independent of device callback size and repaint timing. Map live recording levels over a fixed −58 to −6 dBFS range. The center reaches full height near normal speech peaks while the edges retain room for louder input. [Capture](../../src/capture/audio.rs#L135) · [Recording level mapping](../../src/capture/audio.rs#L274)

Drive all ten bars from the same level. The two center bars react first and all ten can reach full height. Use immediate attack and approximately 73 ms of release smoothing to steady falling bars without delaying rising bars. Publish their heights in one atomic update for both desktop renderers and the dictation preview. [Original centered shape](https://github.com/yosef0H4/SmallTalkAI/blob/b66a0ad/src/capture/overlay_model.rs#L27-L35) · [Packed bars](../../src/capture/overlay_model.rs#L274)

## Meter response and Linux device discovery

OBS uses a fast response for peaks and references −20 dBFS and −9 dBFS in its mixer. These are meter reference points, and published dictation guidance prioritizes clean capture and avoiding clipping. NVIDIA specifies 16 kHz mono for Parakeet TDT 0.6B v3. The waveform conveys level through bar height alone on both desktop overlays. The recorded PCM uses the user's existing configured gain. [OBS mixer](https://obsproject.com/kb/audio-mixer-technical-details) · [JUCE meter ballistics](https://docs.juce.com/master/classjuce_1_1dsp_1_1BallisticsFilter.html) · [Parakeet model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3) · [Google speech capture guidance](https://docs.cloud.google.com/speech-to-text/docs/best-practices)

In two screen recordings, sampled at 30 Hz, the strongest audio-to-bar correlation occurred at roughly 0 ms and 33 ms of visual lag. A partially cropped waveform and independent recorder/capture routes limit interpretation. The unfiltered example changed pixel height about 13 times per second, compared with about 7 in the example where OBS selected Easy Effects Source. The clips used different speech, so this comparison cannot isolate Easy Effects' contribution.

OBS uses the PulseAudio server's source and sink lists and skips sink monitors in its microphone picker. PipeWire's PulseAudio service exposes virtual devices, including the `Audio/Source/Virtual` node created by Easy Effects. SmallTalkAI prefers that server for input and playback, with native PipeWire and ALSA available as fallbacks. Its picker keeps one System default entry and filters server aliases and playback monitors. WirePlumber handles Bluetooth profile selection.
