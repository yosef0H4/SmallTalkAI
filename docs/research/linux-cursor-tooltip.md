# Passive cursor-following status on Linux

Use cursor-following placement on native X11, keep the fixed corner card on KDE Plasma and other Wayland compositors that advertise layer-shell, and use desktop notifications for brief status changes on stock GNOME Wayland. Share the retro card’s rendering across the overlay presenters. Use the same localized status model for notifications, whose appearance is controlled by the desktop.

## What SmallTalkAI does today

Windows reads screen coordinates with `GetCursorPos`, adjusts the tooltip placement against the monitor work area, and moves a native Common Controls tracking tooltip with `TTM_TRACKPOSITION`. Linux maps a shared-memory layer surface at the top-right corner with an empty input region, keyboard interactivity disabled, and exclusive zone `-1`, which allows placement up to the output edges without reserving space. The compositor chooses the output. If layer-shell is missing, the current Linux overlay thread logs the failure and exits. [Windows presenter](../../src/capture/overlay_windows.rs#L455), [Linux presenter](../../src/capture/overlay_linux.rs#L157), [Linux surface setup](../../src/capture/overlay_linux.rs#L417), [Win32 tracking tooltips](https://learn.microsoft.com/en-us/windows/win32/controls/implement-tracking-tooltips)

## What each session can do

**Owned widgets and popups.** GTK’s `query-tooltip` responds to widget hover or keyboard focus. Qt’s `QToolTip::showText` accepts a point from the caller. On Wayland, a GDK popup or an `xdg_popup` uses an anchor relative to its parent surface, with compositor constraints such as flipping at an edge. These APIs can place a tip while the user interacts with SmallTalkAI’s own UI. Desktop-wide following requires a separate source of pointer coordinates. [GTK tooltip signal](https://docs.gtk.org/gtk4/signal.Widget.query-tooltip.html), [Qt tooltip API](https://doc.qt.io/qt-6/qtooltip.html#showText), [GDK popup layout](https://docs.gtk.org/gdk4/struct.PopupLayout.html), [xdg-shell protocol](https://github.com/wayland-mirror/wayland-protocols/blob/main/stable/xdg-shell/xdg-shell.xml#L122)

**Native X11.** Query root-relative pointer coordinates while the card is visible. Move a small override-redirect window near that point and flip or clamp it at the monitor edges. Give the window an empty Shape input region and leave focus with the current app. X.Org’s `xeyes` is a client-side precedent for reading the pointer while it is over other windows. It queries with `XQueryPointer`, using XI2 raw motion to trigger updates when available and a timer otherwise. Use this path for a native X11 session. Xwayland receives its input as a Wayland client, so the presence of `DISPLAY` gives no guarantee of desktop-wide tracking. [XQueryPointer manual](https://www.x.org/archive/X11R7.5/doc/man/man3/XQueryPointer.3.html), [X11 window protocol](https://www.x.org/docs/XProtocol/proto.pdf), [X Shape input regions](https://www.x.org/releases/X11R7.7/doc/xextproto/shape.html), [xeyes pointer query and timer](https://github.com/NetBSD/xsrc/blob/trunk/external/mit/xeyes/dist/Eyes.c#L769-L802), [xeyes XI2 listener](https://github.com/NetBSD/xsrc/blob/trunk/external/mit/xeyes/dist/Eyes.c#L326-L345), [Xwayland architecture](https://wayland.freedesktop.org/docs/book/Xwayland.html)

**KDE Plasma and other layer-shell Wayland.** Detect `zwlr_layer_shell_v1` in the registry. The protocol supplies an output, anchors, and margins for placement. Core `wl_pointer` reports motion in the focused surface’s local coordinates. An empty input region lets events reach the underlying app and also keeps the card from receiving pointer motion. Mako is a client-side precedent for anchored notifications. KWin’s Track Mouse effect follows the cursor because it uses KWin’s own cursor position and compositor scene. This makes it a precedent for compositor-side rendering. [Layer-shell protocol](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-layer-shell-unstable-v1.xml), [Wayland pointer model](https://wayland.freedesktop.org/docs/book/Protocol.html#input), [mako surface placement](https://github.com/emersion/mako/blob/master/wayland.c#L654-L686), [KWin Track Mouse](https://github.com/KDE/kwin/blob/master/src/plugins/trackmouse/trackmouse.cpp#L136-L183)

**GNOME Wayland.** Stock GNOME lacks wlr-layer-shell, so use a transient desktop notification for occasional status changes and show ongoing state in SmallTalkAI’s own UI when open. The shell controls banner placement and timing. GNOME’s built-in Locate Pointer samples `global.get_pointer()` and plays a ripple in the Shell scene. Its implementation calls Mutter’s cursor tracker from inside GNOME Shell. A user-enabled Shell extension could present a following card if exact parity later warrants a GNOME-specific integration. [Layer-shell compatibility](https://github.com/wmww/gtk4-layer-shell#supported-desktops), [Desktop Notifications specification](https://specifications.freedesktop.org/notification/latest-single/), [GNOME Locate Pointer](https://github.com/GNOME/gnome-shell/blob/main/js/ui/locatePointer.js#L14-L35), [Shell cursor tracker access](https://github.com/GNOME/gnome-shell/blob/main/src/shell-global.c#L1084-L1107)

## Implementation direction

Build on the shared overlay model and layout for localized text, Arabic direction, and waveform geometry. Use a compact retro border and high-contrast palette wherever SmallTalkAI draws the card. Keep native window hosting and placement in each platform presenter. The Win32 tracking control can keep its system appearance until shared pixels are needed there. Make the Wayland defaults work with ordinary client permissions. Leave screen capture, raw input devices, and compositor add-ons out of the default path. The ScreenCast portal’s cursor modes belong to screen-sharing streams. A fixed card or a notification needs no such stream.
