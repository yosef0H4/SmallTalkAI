# Native GPU detection for Dictation, Image text, and Read aloud

Dictation uses Parakeet's Vulkan runtime. Image text and Read aloud use the same ONNX Runtime WebGPU library in separate workers. Each runtime should discover its own compatible devices. A working WebGPU adapter remains available when Dictation's Vulkan path fails, and vice versa. [Process architecture](../architecture.md) · [ONNX Runtime WebGPU requirements](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html#requirements)

## Query the WebGPU runtime for its adapter list

Dawn already collects vendor and model names, vendor and device IDs, adapter type, and backend. Its native `Adapter::GetInfo()` returns the model name in `AdapterInfo.device` and the driver description separately. On Linux, Dawn translates Vulkan's physical-device properties. On Windows, its D3D backend reads the name and IDs from DXGI, recognizes software adapters, and uses D3D12 device information to identify integrated graphics. These paths cover NVIDIA, AMD, Intel, and other compatible vendor drivers through the same API. D3D12 discovery may create a device internally to query capabilities. [Dawn adapter info implementation](https://dawn.googlesource.com/dawn/+/refs/heads/main/src/dawn/native/Adapter.cpp) · [Vulkan metadata](https://dawn.googlesource.com/dawn/+/f0fd8aa43e3de2ab04ed40259f1e92bf0be89387/src/dawn/native/vulkan/PhysicalDeviceVk.cpp) · [DXGI metadata](https://dawn.googlesource.com/dawn/+/67fb117be46c9bae87cbc1e4d25256af93533579/src/dawn/native/d3d/PhysicalDeviceD3D.cpp) · [D3D12 discovery](https://dawn.googlesource.com/dawn/+/dda36f339fa813b06536733b6580b0203d585c94/src/dawn/native/d3d12/PhysicalDeviceD3D12.cpp)

The adapter list should come from the same ONNX Runtime WebGPU provider that opens the device. ORT's `adapterIndex` is relative to Dawn's enumeration with specific backend and power-preference options. General ORT device inventory returned both PCI GPUs even when Dawn could only run on the Radeon on the test laptop. A standalone Dawn build can also use different options or a different revision, so its index has no guaranteed relationship to the packaged provider's index. [ORT WebGPU selection semantics](https://github.com/microsoft/onnxruntime/blob/main/plugin-ep-webgpu/python/onnxruntime_ep_webgpu/README.md) · [Dawn adapter options](https://dawn.googlesource.com/dawn/+/refs/heads/main/docs/dawn/features/adapter_options.md)

## Maintain a small dependency patch

1. Pin an obtainable ONNX Runtime source revision and its matching Dawn dependency. Use the same WebGPU provider configuration for Linux and Windows that the two SmallTalkAI workers load. The application already applies a source patch to Sherpa-ONNX as part of packaging. Keep an ORT patch beside it and have release CI check that it applies cleanly whenever the dependency is updated. The shipped npm binary is `1.31.1`. It reports build revision `41d4d61f1`, and Microsoft's NuGet manifest identifies the full commit `41d4d61f14b9c1dd0b2ccda1e9b85dd415fd0496`. Software Heritage has the corresponding source tree, including the provider's indexed enumeration and its Dawn dependency pin. [Runtime catalog](../../assets/catalog/downloads.json) · [Microsoft NuGet manifest](https://api.nuget.org/v3-flatcontainer/microsoft.ml.onnxruntime/1.31.1/microsoft.ml.onnxruntime.nuspec) · [Archived source tree](https://archive.softwareheritage.org/browse/revision/41d4d61f14b9c1dd0b2ccda1e9b85dd415fd0496/) · [Dawn adapter query patch](../../scripts/onnxruntime-webgpu-adapters.patch) · [ORT build flags](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html#build-flags)
2. Share the provider's adapter enumeration and options between selection and a small versioned native query. Return the original index, name, type, backend, and vendor/device IDs. Copy the returned strings before releasing Dawn's adapter info. Expose an optional native identity where available, such as Vulkan's device UUID. A Windows adapter LUID identifies the adapter within the running Windows session. The displayed name and vendor/device IDs alone cannot distinguish identical cards. [Dawn adapter info implementation](https://dawn.googlesource.com/dawn/+/refs/heads/main/src/dawn/native/Adapter.cpp) · [Vulkan device IDs](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceIDProperties.html) · [Microsoft LUID docs](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-luid)
3. Enumerate on demand in a short-lived helper using the packaged provider. Read metadata without running a model or compute shader on each adapter. Drop entries classified as CPU/software while retaining the original indices so removing an entry cannot send inference to the wrong GPU. For zero or one GPU, hide the picker. When there are two or more, show their full names and adapter types. Use the first compatible dedicated GPU in provider preference order until the user chooses a device. Keep a refresh button for driver and hardware changes. Re-resolve the user's saved identity against current metadata before passing an index to the worker.
4. Build and verify packaged runtime artifacts in Linux and Windows CI. Check software exclusion and index preservation with fixtures, then test one explicitly selected adapter at a time on designated hardware and confirm the device the worker created. Keep device discovery separate from a model smoke test, since an enumerated adapter can still fail a model's runtime requirements. Use the controlled test machine for driver and inference checks.

Keep the existing ONNX Runtime C ABI and package filenames, including the Linux `libonnxruntime.so.1` SONAME used by Sherpa. The metadata query is an optional versioned export in the same runtime. Verify the bundle's library dependencies and update its pinned artifact hash when switching the catalog to patched builds. ## Prior laptop investigation

This evidence comes from the previous workload-based experiment. The native adapter query supersedes its use of Linux process accounting, Windows video-memory changes, or repeated workload execution for names.

The Ryzen 7 5800U laptop exposes two separate PCI graphics devices. `01:00.0` is the dedicated NVIDIA GeForce RTX 3050 Ti Mobile (`10de:25a0`, `renderD129`). `05:00.0` is the integrated Radeon (`1002:1638`, `renderD128`). The loaded NVIDIA kernel module was `620.70.06`. The module on disk and user-space driver libraries were `620.73.04`. NVIDIA-only Vulkan returned `VK_ERROR_INCOMPATIBLE_DRIVER`. Radeon-only Vulkan identified an integrated GPU with Vulkan 1.4, compute queues, and 16-bit storage support. This is a driver failure on a present dedicated GPU.

The published archive matched the catalog SHA-256 and the extracted library reported version `1.31.1`, build commit `41d4d61f1`. With no plugin registered, `GetAvailableProviders` listed `WebGpuExecutionProvider` and `GetEpDevices` returned NVIDIA `10de:25a0` and AMD `1002:1638` WebGPU entries. The probe appended `WebGPU` with `adapterIndex=0` and disabled CPU fallback. A separate process with `adapterIndex=999` failed session creation and reported two Dawn adapters. [Microsoft release artifact](https://registry.npmjs.org/onnxruntime-node/1.31.1) · [Download catalog and hash](../../assets/catalog/downloads.json)

On the hybrid Linux laptop, each test process used `VK_DRIVER_FILES` to expose a single driver to the Vulkan loader. The Radeon-only run produced all 64 expected float32 ONNX `Add` outputs. The NVIDIA-only run failed during Dawn Vulkan initialization with `VK_ERROR_INCOMPATIBLE_DRIVER` and zero Dawn adapters. `GetEpDevices` still returned both WebGPU entries in both processes. The OS-visible EP devices therefore remained the same while actual WebGPU execution changed with the selected ICD. [Khronos Vulkan loader driver discovery](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md#overriding-the-default-driver-discovery)

With `620.70.06` NVIDIA libraries matching the loaded kernel module in an isolated process, NVIDIA-only Vulkan and WebGPU both ran on the RTX 3050 Ti. With both drivers available, Dawn index 0 ran on the RTX and index 1 ran on the Radeon. The NVIDIA driver exposed no DRM engine counters for the probe. NVML attributed the compute context to the probe's PID on the RTX, while the Radeon run reported its PCI address through DRM counters. Merely opening the NVIDIA device or allocating graphics memory was insufficient because Dawn also did that when the Radeon ran the graph. [NVML process accounting](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html)

The packaged Windows device API and per-model support remain unverified by this probe. GitHub did not return the pinned source tag or build commit during research, so the 1.31.1 observations here come from the published Linux binary.
