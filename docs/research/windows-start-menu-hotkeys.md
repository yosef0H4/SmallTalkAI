# Windows Start menu and shortcut holds

The reported sequence is using the CapsLock shortcut as Windows Search closes, AutoHotkey warning that it received 71 hotkeys in 1,625 ms, and the SmallTalkAI shortcut tooltip staying visible. The installed profile uses bare CapsLock to show shortcuts while held. The enabled registrations reviewed for the incident did not include a Win chord.

## What the sources establish

- AutoHotkey v2 defaults to 70 hotkey activations in 2,000 ms. Auto-repeat can reach this limit, and the warning reports an aggregate count without naming the keys. The runtime checks the rate before calling the script handler, so a down handler that immediately returns on a repeat can still contribute to the count. [AutoHotkey rate limit](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/A_MaxHotkeysPerInterval.htm), [AutoHotkey dispatch source](https://github.com/AutoHotkey/AutoHotkey/blob/v2.0/source/hotkey.cpp#L830-L896).
- An ordinary script message box allows interruptions. The built-in rate warning explicitly disables script interruption while it is displayed, clears buffered re-runs, and skips the activation that triggered it even if the user chooses Yes. If that activation was a key-up hotkey, its release callback is skipped. This is a possible route to stale hold state. Which hotkey triggered the reported warning is unknown. [AutoHotkey dialog behavior](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/Thread.htm), [AutoHotkey warning source](https://github.com/AutoHotkey/AutoHotkey/blob/v2.0/source/hotkey.cpp#L830-L896).
- Windows routes ordinary key messages to the focused window and calls a low-level keyboard hook before the event is posted to the target thread. Windows documents hook-chain suppression and silent removal after a hook timeout. AutoHotkey documents masking some Win and Alt events to prevent menu activation. The reviewed sources do not establish Start dismissal as a cause of lost global-hook key-up events. [Microsoft keyboard input overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input#keyboard-focus-and-activation), [Microsoft low-level keyboard hook](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc), [AutoHotkey menu masking](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/A_MenuMaskKey.htm).

## What was reproduced

An isolated native AHK harness called the actual CapsLock down handler without registering a global hotkey or sending input and withheld the up callback. After 870 ms the hold property was still set while Windows' asynchronous CapsLock state was up. Calling the normal up handler removed the property. Before the fix, the Windows overlay used the presence of that property as its held state. This reproduced the app-side stale state with a withheld release. The exact Start-menu sequence still needs a desktop trace. [AHK hold publisher](../../ahk/lib/Hotkeys.ahk), [Windows overlay reader](../../src/capture/overlay_windows.rs).

## Fix and verification

Both the CapsLock down callback and the callback for a chordâ€™s main key now wait for release with one thread per hotkey and repeat buffering off. The up handler and the wait completion share the same cleanup. A visible hint carries a 600 ms deadline. AutoHotkey renews it every 100 ms while its hook reports the triggering key down, and the native overlay enforces the deadline independently. Windows updates its asynchronous key state after low-level hooks accept the event, so the OS state alone can miss a deliberately suppressed down. [AutoHotkey KeyWait example](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/KeyWait.htm), [AutoHotkey thread limit](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/_MaxThreadsPerHotkey.htm), [AutoHotkey dispatch admission](https://github.com/AutoHotkey/AutoHotkey/blob/v2.0/source/application.cpp#L877-L894), [Microsoft asynchronous input behavior](https://devblogs.microsoft.com/oldnewthing/20140213-00/?p=1773).

To confirm the reported trigger, capture the physical shortcut down and up in AutoHotkey's key history alongside the script callbacks, hold property and warning timing while dismissing Start. Verify one long hold through auto-repeat, release with Start open and while it closes, and confirm that a stalled publisher lets the visible tooltip expire. [AutoHotkey KeyHistory](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/KeyHistory.htm).


The local shell log showed a recording began before the screenshot and the corresponding hotkey-up callback arrived about 90 seconds later. That provides evidence of delayed recording cleanup alongside the reproduced hint latch.

A read-only token check on the affected machine found AutoHotkey at medium integrity, Windows Search (`SearchHost`) at low, Start (`StartMenuExperienceHost`) at medium, and Task Manager at high. An elevated target can block synthetic input under UIPI. These observations do not support higher integrity as the explanation for the reported Search case. [Microsoft integrity levels](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works), [Microsoft SendInput restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

On a private Windows desktop, the real AutoHotkey publisher and native overlay ran in separate processes at normal privileges. The tooltip stayed visible during renewals, normal release closed it, and a stalled publisher left it visible for 0.617 seconds before it closed. A subsequent hold reopened it. The user subsequently confirmed that the test installer fixed the physical CapsLock sequence in Windows Search.

## Settings shortcut recorder audit

The Windows Settings recorder had its own CapsLock hotkey pair. Its down callback returned immediately, and shortcut capture excluded CapsLock as an ending key. Repeats could therefore reach AutoHotkeyâ€™s hotkey rate counter while capture kept waiting. The helper now captures CapsLock with its existing InputHook, suppresses the system toggle, and reads the physical modifier state when constructing the shortcut. A CapsLock release completes the capture only when Settings allows the standalone key. [AutoHotkey InputHook key options and callbacks](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/InputHook.htm#KeyOpt), [AutoHotkey hotkey dispatch](https://github.com/AutoHotkey/AutoHotkey/blob/v2.0/source/hotkey.cpp#L762-L825).

The initial InputHook implementation could lose Caps Lock after the letter ended capture. In a Windows test, Caps Lock+C reached the recorder as C while the post-capture Caps Lock state was up. The recorder now builds the chord from ordered key-down and key-up events. A lone key produces an inline warning that names the detected key.

An isolated Windows Settings test recorded Caps Lock+C for Copy screen text and Caps Lock+W for Read selection, then saved and reloaded both bindings. It also verified the warning for C alone, standalone Caps Lock for Show shortcuts, and Escape cancellation.

The recorder also outlived Settings when its window closed during capture. A native headless reproduction left the AutoHotkey child running on the baseline. After attaching the recorder to the existing Windows kill-on-close job, the same test stopped the child when Settings exited.
